## Early review notes for Claude

1. `packages/core/src/chain/profiles.ts`: `assertRpcAllowed` currently builds the origin from protocol + hostname, omitting the port despite its documentation. Public RPC on an unapproved port is therefore accepted. Use exact `URL.origin` for public profiles; authorize the owned local node's actual ephemeral origin separately. Test a changed public port. Treat redirects separately at the HTTP client.
2. `assertBroadcastAllowed(profile, operatorApprovalId)` checks only that a string is nonempty. This is not an approval verifier. Ensure every real public signing/broadcast entry point checks a durable, operator-issued approval tied to the exact plan digest, limits and expiry; for M1a, keeping all public writes unconditionally disabled is acceptable. A caller-created string must never enable signing. Reassess once the signer is written.
3. Contract fixture preliminary read: validAfter/validBefore bounds, domain hashing, authorization nonce consumption, payee binding for receive and signature validation are present. This is not acceptance; inspect tests for wrong chain/token/domain/payer, expiration, replay and cancellation before approving.
4. The live finalized-block lag was 660 seconds on testnet in the sample. Keep public settlement pending/resumable when waiting exceeds the HTTP deadline; do not recheck signature expiry as though an already-included valid transfer were invalidated by later finalization.
5. **P1: filesystem store does not provide the promised atomic budget transaction.** `packages/core/src/state/store.ts` serializes only per instance, while each process/instance can read the same old ledger and overwrite the other's spend. `commitSpend` also separates increment from limit checking. Prefer SQLite transactions/unique constraints (Node's built-in `node:sqlite` is available in the supported runtime) instead of implementing cross-process financial transactions in JSON files. Reserve budget + idempotent authorization atomically, enforce the limit inside the transaction, and test two independent store handles/processes against the same database.
6. **P1: intent-path collisions.** `safeSegment` accepts colon and underscore then replaces colon with underscore, so `intent:123` and `intent_123` address the same intent file. This contradicts its collision rejection claim and could overwrite another intent when IDs come from a caller. Store exact IDs as database keys (preferred), hash the complete ID, or reject noncanonical IDs; test this pair. Do not normalize distinct opaque IDs onto one key.
7. **P2: claim visibility/durability.** `claimOnce` exposes the O_EXCL-created file before writing its value, so a concurrent reader or post-crash reader can observe an empty claim. Directory fsync failures are also swallowed indiscriminately despite fail-closed durability requirements. These problems further favor SQLite transactional state. Keep an explicit single-process audit writer or a database-backed sequenced audit ledger.
8. **P1: concurrent audit appends reuse sequence/hash.** `packages/core/src/audit/log.ts` computes seq/prevHash before its first await and updates them only after file writes. `Promise.all([log.append(a), log.append(b)])` therefore creates two records with the same sequence and parent hash even on one instance. Allocate and append transactionally (or enforce one serialized writer), validate the chain when reopening, and add a concurrent-append/restart test. Merely declaring the log single-writer does not serialize concurrent requests within that writer.
9. **P1: embedded signatures survive error redaction.** `audit/redact.ts` retains Error.message and uses whole-string anchored hex matching. `redact(new Error('authorization: 0x' + 'ab'.repeat(65)))` preserves the entire synthetic signature, and `assertNoSecretMaterial` also accepts it. Never log arbitrary upstream messages; emit bounded stable codes and explicitly allowlisted data. Test embedded signatures/bearer strings/secret-sentinel error messages, not only fields named privateKey. A 32-byte private key cannot be distinguished from a transaction hash by length; enforce context-specific field allowlists at key-bearing process boundaries.
10. **P2: audit verifier accepts invalid lifecycle ordering.** `audit/verify.ts` finds any last terminal state and checks only whether settlement/delivery kinds occur somewhere. It can accept a delivery event before settlement, or DELIVERED followed by RESERVED. Validate the per-intent legal state/event sequence, settlement-before-delivery, required linkage fields and actual final state. Add negative tests against a correctly rehashed but semantically invalid log; hash integrity alone does not establish a valid payment lifecycle.
11. **P1: reservation replay does not validate the request binding.** Executed a temporary review reproduction against the compiled SQLite store: reserve 100 units for principal A, then request 900 units for principal B under the same intent/idempotency IDs. The second call returned `ok:true, replayed:true` with A's 100-unit reservation. The store must reject changes to principal, policy, normalized asset/amount legs and immutable intent/request digest. Do not rely on callers noticing the returned amount differs before signing. Test altered amount, principal, asset and body/quote binding on retry, including after restart.

Reproduction note: item 9 was also executed with a synthetic 65-byte marker (not a real key or authorization). The marker survived redaction and the no-secret assertion accepted it. No real credentials or funds were used in either review reproduction.

12. **P1: signer issues multiple spendable authorizations against one reservation.** Executed a local HTTP reproduction against the compiled signer, using a generated in-process disposable key, dummy asset/payee, and no chain/broadcast. Three requests with identical intent/idempotency/quote/100-unit amount but distinct authorization nonces all returned HTTP 200 with three distinct signature digests. The policy total budget was 200; the durable committed budget stayed at 100. Thus 300 units were authorized against a 100-unit reservation. Fix item 11 at the actual signing boundary: atomically bind each intent/idempotency key to the entire immutable authorization digest including nonce, validity, domain, payer/payee, amount, quote/request identity and policy. A changed nonce must conflict; identical retry must not create a new spend capability. No keys, signatures or transport credentials were emitted by the reproduction; only counts/statuses/budget totals were observed. Add this as a signer HTTP regression, including concurrent requests.

13. **P2: settlement's authorization binding is optional despite the safe-delivery contract.** `SettlementExpectation.authorizationNonce` is optional, and the verifier can return `status:final` with `authorizationBound:false`. This milestone only supports EIP-3009, so make the nonce mandatory and fail closed at runtime if absent. Preserve and compare the receipt's transaction hash with the requested hash rather than copying the requested value into verified facts. Add absent/wrong nonce and wrong receipt-hash tests. Callers must not accidentally release a service on an unrelated matching transfer.

Item 10 reproduction was also executed: a synthetic correctly hash-chained log with states DELIVERED → FINALIZED → RESERVED and delivery before settlement returned `ok:true`, claimed terminal DELIVERED, and no errors. This establishes a semantic verification defect independent of hash corruption.

14. **P2: dependency audit currently fails for solc → tmp.** `npm audit --omit=dev --json` reported installed tmp 0.2.6 and its high-severity advisory [GHSA-7c78-jf6q-g5cm](https://github.com/advisories/GHSA-7c78-jf6q-g5cm), patched in 0.2.7. This is a dependency finding; exploitability through our compiler path has not been established. Prefer a reviewed patched resolution/override and rerun fixture compilation plus dependency audit; do not run `npm audit fix --force` indiscriminately. Align the documented/CI/runtime Node requirement with the actually tested built-in SQLite API (local Node 24.18.0).

15. **Upstream reuse correction:** OpenZeppelin 5.0.2 is Shanghai-compatible on the exercised dependency graph. Downloaded the exact official npm package separately from the working tree and compiled a minimal ERC20 + EIP712 + ECDSA contract with solc 0.8.38, evmVersion=shanghai, optimizer runs=200: 14 imported files, zero errors, 4,203-byte creation code. Prefer the pinned upstream EIP712 base over an inline replacement. This is compiler evidence for the exercised graph, not a production security endorsement. Continue testing the complete fixture on the Shanghai node.

16. **P2: legitimate exact signer retry fails when the original payment filled the budget.** HTTP recheck after item 12's fix: with amount=100 and totalBudget=200, nonce sequence [1,1,2,3] returns [200,200,409,409], one distinct signature and committed=100 (budget bypass corrected). With totalBudget=100, the same sequence returns [200,403,403,403] because evaluateQuote adds the already-reserved amount again before replay detection. An identical retry after a lost response must be recognized against the immutable binding before checking incremental budget; a changed request must still conflict. Test a payment exactly equal to its total budget.

17. **P2: audit redaction changes an already-computed signature digest.** `redactPayload({signatureDigest: 'sha256:' + 'a'.repeat(64)})` returns a different digest because the key-name branch hashes every string, including existing digests. This breaks direct linkage between signer response/intent and the audit record. Keep explicitly digest-valued, schema-validated fields unchanged; reduce raw signatures to digests. Add a digest-idempotence regression. Also remove raw `error.message` from signer `main.ts`'s fatal output so the key-bearing entrypoint follows the same stable-error-code rule.

18. **P1: facilitator's draft broadcast path lacks durable deduplication and enforced gas policy.** `apps/facilitator/src/service.ts` currently logs an attempt then delegates every `/settle` request to upstream, with unbounded `walletClient.writeContract/sendTransaction` passthrough. The signer's notional gas reservation does not constrain this separate gas account. Concurrent/replayed requests may spend extra gas; a crash after broadcast but before the result append loses the hash needed for reconciliation. Before acceptance, constrain allowed token/payee/call types, enforce sponsor gas/fee and total budget ceilings at the broadcast boundary, atomically bind an idempotent settlement to the authorization, and durably record the transaction hash/nonce before broadcast (compute locally from a prepared signed transaction without exposing or persisting its raw contents). Ambiguous outcomes must reconcile rather than resubmit. Test duplicate/concurrent settlement, gas-cap rejection and crash after broadcast. A `settle.attempt` audit event alone is not an idempotency or recovery mechanism.

19. **P1 follow-up to the constrained broadcast rewrite: uncertain sender nonce can be reused.** Executed a mock-only test of the compiled constrained writer: first send throws a simulated lost response; the RPC's pending nonce remains 0; a second authorization is then signed and sent with sender nonce 0 again. Observed allocated nonces `[0,0]`, two send attempts, first threw/second returned. No key or network was used. In real execution this may replace or conflict with the unresolved first transaction. Serializing calls to `getTransactionCount(pending)` does not reserve a nonce durably. Persist sender nonce ownership by chain/account and reconcile uncertain submissions before allowing conflicting work; test stale pending RPC views plus restart. Also scope authorization dedupe by chain + asset + payer + nonce and bind immutable transfer terms, rather than omitting the asset and returning an unrelated old hash. The facilitator needs its own operator payee allowlist; comparing only with caller-supplied paymentRequirements is not that allowlist.

20. **P1: buyer's claimed request/result verification is missing.** In SDK `requestPayment`, `expectedRequestDigest = quote.requestDigest` compares the quote with itself, rather than recomputing the digest from the actual input and resource path. The delivered result is also only cast to DigestServiceResult and hashed; it is not schema-validated or compared with the expected SHA-256 of the requested input. Recompute and compare request binding before signing, validate response schema, and verify the actual deterministic result. Add wrong-input and corrupt/wrong-result tests that exercise SDK behavior.

21. **P1: buyer durability and pending handling occur after the paid HTTP operation.** The authorization nonce/reservation/signature digest are persisted only after awaiting paidFetch. A crash or dropped HTTP response after settlement can therefore leave an intent without the nonce/hash required for recovery. Re-entry through wrapFetch generates a fresh nonce and collides with the now-correct signer binding. Persist public authorization terms before the signature reaches the paid HTTP send, and resume the original authorization or reconcile by its persisted identity. HTTP 202 is `response.ok === true`, so the existing 202 branch nested under `!response.ok` is unreachable; it proceeds toward a missing receipt instead. Treat pending/ambiguous outcomes explicitly, persist any known settlement hash before finality, and never label a transport/server failure as definitive DENIED after a possible broadcast. Test crash/lost response after submission and 202→finalized resumption.

22. **P1: seller replay/recovery path is behind fresh-payment middleware and holds settlement only in memory.** A replay first passes paymentMiddleware, which normally rejects a consumed EIP-3009 nonce, before the durable delivery cache is reached. Retrying via the SDK also creates a new authorization. Quote expiry is checked before recovery, so already-paid requests cease being recoverable on expiry. Persist a unique authorization→immutable quote/body binding before settlement, and route authenticated/bound replay/reconciliation to stored settlement/result before asking for a new payment. The current delivery key includes quoteId, so it does not itself prevent one authorization from being claimed under a different quote. Persist settlement facts from onAfterSettle instead of relying only on `settlements: Map`; keep stable per-payment IDs across retries. Test same request sequentially/concurrently, seller restart, quote expiry after inclusion, and old proof used for a different quote/body.

23. **P2: reported deployed code digest still hashes compiler placeholders.** `apps/localchain/src/provision.ts` now correctly masks immutable ranges for template comparison, but returns `artifact.deployedBytecodeDigest` as the token's deployed runtime digest. Hash the actual `eth_getCode` bytes for deployment evidence; keep the compiler template digest separately. Also strengthen demo concurrency acceptance: its current `Promise.allSettled` check can pass when both duplicate calls reject. Require successful retrieval of the same result/receipt for each duplicate, and race first-time submissions in integration tests rather than only duplicates of an already-delivered request.

26. **P1 follow-up to result recovery: recovery path does not verify the deterministic answer.** `tryRecoverDelivery` validates only DigestServiceResultSchema, unlike the initial delivery path's SHA-256 comparison with input. Retain a known transaction hash before awaiting finality, and avoid terminal DENIED after a possible broadcast (item 21 remains partially open).
