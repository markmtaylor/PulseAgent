# Runbook

Operating procedures for milestone 1a. Everything here concerns the local
rehearsal; there is no public-chain procedure because there is no public-chain
code path.

## Starting the stack

`npm run demo:local` brings up everything and tears it down. For anything else,
`examples/two-agents/src/harness.ts` is the same wiring as a library:

1. A disposable EVM is started in-process, on loopback, at chain id 31337, held
   at the Shanghai hardfork. It starts with no owned accounts, so there is no
   well-known development key anywhere in the system.
2. The fixture token is compiled for Shanghai and deployed; the runtime bytes are
   read back with `eth_getCode` and compared against the compiled output, with
   the compiler's immutable ranges masked.
3. Ports are reserved before any service starts, because the signer's policy must
   name the seller's origin and the seller must name the facilitator's.
4. The signer, facilitator and seller start as separate processes. Each prints one
   JSON readiness line containing public information only.
5. The buyer funds the payer with valueless test tokens and the facilitator with
   native gas. The payer holds no native balance: under EIP-3009 the facilitator
   sponsors gas.

Stop with the harness's `stop()`, which terminates children in reverse order and
closes the chain. The demo calls it in a `finally` handler, so a failed run does
not leave processes behind.

## Configuration

| Component | Where its configuration comes from |
| --- | --- |
| Signer | `PULSEAGENT_SIGNER_POLICY` (policy JSON), `PULSEAGENT_SIGNER_DB`, `PULSEAGENT_SIGNER_TOKEN`, `PULSEAGENT_SIGNER_PORT` |
| Facilitator | `PULSEAGENT_FACILITATOR_CONFIG` (JSON), `PULSEAGENT_FACILITATOR_TOKEN` |
| Seller | `PULSEAGENT_SELLER_CONFIG` (JSON), `PULSEAGENT_FACILITATOR_TOKEN` |
| MCP server | `PULSEAGENT_POLICY`, `PULSEAGENT_DB`, `PULSEAGENT_RPC_URL`, `PULSEAGENT_SIGNER_URL`, `PULSEAGENT_SIGNER_TOKEN`, `PULSEAGENT_OWNED_LOCAL_ORIGINS` |

No component accepts key material. Transport tokens are generated by whatever
starts the processes and passed through the environment.

## Reading the evidence

A run writes to `.runtime/demo-<timestamp>/evidence/`:

- `manifest.json` — what was claimed, including the settlement facts, the
  balances before and after, the fixture's on-chain code digest, and each log's
  terminal hash
- `audit-platform.jsonl` — the buyer, seller, facilitator and verifier records
- `audit-signer.jsonl` — the signer's own records, on its side of the boundary

Verify a run with:

```bash
npm run audit:verify -- --manifest .runtime/demo-<timestamp>/evidence/manifest.json
```

That checks each chain, the lifecycle ordering within each log, the manifest's
own claims against the logs, and the payment's complete lifecycle across both
logs. Pin the terminal hashes somewhere outside the run: without them a removed
tail is undetectable.

## When a payment does not complete

The rule throughout: **an unknown outcome is never a reason to pay again.**

| Symptom | What it means | What to do |
| --- | --- | --- |
| `202` from the seller | Settled but not final under the chain's rule | Retry with the same idempotency key. The transaction hash is already saved. |
| Buyer reports `RECONCILING` | An authorization exists and its delivery could not be recovered yet | Retry with the same idempotency key. No new authorization will be issued. |
| `authorization_already_bound` | This intent is bound to one authorization already | Use a new idempotency key for a genuinely new payment; retry the same key to recover this one. |
| Facilitator reports `settlement_outcome_unknown` | The broadcast's result is unknown | Retry. The claim and hash are recorded, so the same transaction is returned rather than a second one. |
| `settlement_not_verified` | The chain does not support the facilitator's claim | Do not deliver. Investigate: wrong amount, wrong payee, a non-canonical block, or a reverted transaction. |
| `broadcast_refused:*` | The broadcast boundary refused | Nothing was sent. Read the code: asset, payee, function, fee cap or budget. |

Resolve a pending payment with `verify_settlement` (MCP) or
`verifyIntentSettlement` (SDK). Both read; neither pays.

## Recovering a paid-for result

If a buyer paid and lost the response, it holds the authorization nonce and can
collect the result from the seller's `/receipt` endpoint. The SDK does this
automatically on a retry with the same idempotency key. The recovered result is
re-verified against the chain and recomputed from the paid-for input before it is
accepted: a stored record is still only a record.

If the seller's record is gone, the payment is still visible on chain and in the
audit trail, and the buyer is owed a result. There is no automated remedy for
that in this milestone, which is a real limitation and not a bug to work around
by paying again.

## Public-chain operations

There are none. `npm run demo:testnet:plan` writes an unsigned plan with the
operator-supplied values left visibly unresolved.
`npm run demo:testnet:execute` fails and names what is missing. Chain 943 has no
verified approval record, no approved test asset and no funded sponsor; chain 369
is read-only.

Do not attempt to work around this by pointing a local configuration at a public
RPC. The chain profiles refuse it, and the refusal is the feature.

## Rotating a compromised signer

The signer's key exists only in memory. Restarting it generates a new one, which
means a new payer address, which means the operator policy and any funding must
be updated. There is no key export and no migration path, by design: a key that
could be moved would have to exist somewhere it could be read.

If a signer process is believed compromised, stop it, treat every authorization
it issued as spendable until the corresponding nonces are consumed or cancelled
on chain, and start a fresh one. `cancelAuthorization` on the fixture token burns
an unused nonce.
