# Security

## Reporting

Report a suspected vulnerability through a GitHub private security advisory on
this repository rather than a public issue, and include what you did, what
happened, and the commit you tested. If you are unsure whether something is a
vulnerability, report it anyway.

Please do not open a public issue for anything that could let someone else take
funds, bypass a policy limit, or obtain a signature.

The requirements this implementation was built against are in
[`docs/SECURITY-MODEL.md`](docs/SECURITY-MODEL.md); what follows describes what
the code actually does.

## What this software is

Milestone 1a: a local rehearsal. It performs real payments on a disposable local
chain with a valueless test token. It has never paid anything on a public chain,
and it has no code path that could. Treat it as a working demonstration of a
design, not as something to put money behind.

## Trust boundaries

**The signer.** `apps/signer` is a separate process. It generates its own key,
the key never leaves it, and only public addresses are ever emitted. It enforces
its own copy of the operator policy and will not sign anything but an EIP-3009
`TransferWithAuthorization` that its policy approves. There is no generic signing
endpoint, no key import, no key export, and no flag from a caller that carries
authority.

Process separation on one OS user prevents accidents. It does not resist a
compromised host: a process running as the same user can read the signer's files
and, on most systems, attach to it. Production custody requires at minimum a
separate OS identity or container, and realistically an external signer, a KMS or
an HSM.

**The model boundary.** MCP is an interaction boundary, not an authorization
boundary. A model can request a quote, request a payment under an operator's
policy, read status, verify a settlement and read the audit trail. It cannot
approve a budget, change a policy, choose an RPC endpoint, reach a key, or
request a signature over data of its choosing — those tools do not exist, so
there is nothing to call. Tool errors report stable codes and locally written
descriptions; no upstream message is forwarded, because an upstream message is
arbitrary text and has been observed carrying embedded signature material.

**The broadcast boundary.** The facilitator's gas account is separate from the
buyer's, and the buyer-side signer's gas reservation says nothing about it. So
every broadcast is constrained to `transferWithAuthorization` on an allowlisted
asset to an allowlisted payee for the exact amount the settlement names, with an
explicit gas limit, explicit fee caps and a lifetime fee budget. One
authorization may be broadcast once; the claim and the sender nonce are taken in
one transaction, and the transaction is signed locally so its hash is recorded
before it is sent.

**The chain boundary.** A chain is usable only if it has a profile. Unknown
chains are disabled. RPC endpoints are compared on the exact origin, so an
approved host on an unapproved port is refused. The local profile additionally
requires a loopback literal and an origin this process tree started. Every node's
self-reported chain id is checked.

## Handling of secrets

- No private key, seed phrase, keystore or password is read from configuration,
  accepted as an argument, or written anywhere. Keys are generated inside the
  process that needs them.
- Audit records at the key-bearing boundary are built from an explicit field
  allowlist: a field not on the list is a thrown error, not a redacted value.
  This is necessary because a 32-byte private key and a 32-byte transaction hash
  are the same length and the same alphabet, so nothing can separate them by
  inspection.
- Signatures are recorded as digests. A raw EIP-3009 authorization plus its
  signature is replayable value and is never persisted or logged.
- Transport tokens are generated by the parent process, passed through the child's
  environment, and never logged or written to evidence.
- Fatal errors from the signer, facilitator, seller and MCP server print a stable
  code and the error's class name. They do not print messages.

## What the audit trail proves

Records are hash-chained, so an edited or removed interior record is detectable
from the records that follow it, and the verifier also checks lifecycle ordering:
a delivery before its settlement, or a record continuing an intent after a
terminal state, is a finding even when every hash is valid.

It does not prove the log is the original one. Whoever can write the database can
rebuild a consistent chain or drop its tail. Detecting a removed tail needs the
terminal hash recorded somewhere else, which is what the exported manifest is
for. Independent anchoring and write-once retention are controls this build does
not provide.

## Known limitations

- A dishonest seller is not addressed. One result per payment is proven; service
  quality, escrow and disputes are not.
- Contract-wallet payers are out of scope. The test fixture verifies ECDSA only.
- Fee-on-transfer, rebasing and upgradeable-proxy tokens are unsupported and
  untested.
- Single host, single instance. The durable store gives real transactions and
  real uniqueness on one machine, not replication.
- The seller's receipt-retrieval endpoint is unauthenticated in this milestone.
  That is acceptable only because the authorization nonce is already public in
  the chain's `AuthorizationUsed` event and this service's output is recomputable
  by anyone. A service selling anything confidential must authenticate the buyer
  there, and this build does not implement that.

## Reproductions

If you are testing this software, use the disposable local chain. Do not point
any part of it at a public endpoint with a funded account: there is no approval
path, the attempt will be refused, and a funded account in a test harness is a
hazard regardless.
